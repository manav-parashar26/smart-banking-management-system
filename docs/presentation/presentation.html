Slide 02
Problem Statement
Bridging the divide between theoretical textbook algorithms and real-world banking systems

Traditional Academic Limitations

  • Trivial CLI Scopes: Most educational banking projects focus strictly on primitive CLI balance mutations (add/subtract numbers).
  • Monolithic Structures: Zero separation of concerns; accounts, ledgers, and credentials are often merged into flat structs.
  • Insecure Credentials: Passwords and PINs are commonly stored as plaintext strings or rudimentary Caesar ciphers.
  • Zero Concurrency & Networking: No real-world web transport, network protocol handling, or REST APIs.
  • Volatile or Flat Data: Inability to demonstrate relational algebra, ACID guarantees, or 3NF normalization.

The Smart Banking Enterprise Paradigm

  • Full-Stack Architecture: Decoupled multi-tier system with C++17 core engine, Winsock2 REST API, and React 18 frontend.
  • Advanced OOP & Polymorphism: Abstract account hierarchies dynamically handling interest calculation and overdraft limits.
  • Rigorously Benchmarked DSA: 9 STL containers and graph algorithms solving real financial throughput problems.
  • Cryptographic Security: NIST SP 800-132 PBKDF2-HMAC-SHA256 salted PIN hashing with constant-time verification.
  • Forensic AML Compliance: Directed transaction graph modeling with automated cycle detection for wash trading.

Key OOP Principles Demonstrated

  • Encapsulation: Private data members (m_balance, m_pinHash) are strictly protected. State mutations occur exclusively via validated public member functions.
  • Abstraction: Account exposes a clean public interface (deposit, withdraw, calculateInterest) while encapsulating double-entry logging mechanics.
  • Inheritance: SavingsAccount and CurrentAccount inherit common accounting logic while extending specialized banking fields.
  • Polymorphism & Virtual Dispatch: Dynamic dispatch via std::shared_ptr<Account> ensures correct derived withdrawal limits and interest rates execute at runtime.
  • Centralized Exception Handling: Domain exceptions are caught in HttpServer.cpp and mapped to HTTP status codes (400, 401, 403, 404, 422).

Account Specialization

  • Savings Account: Enforces minimum balance ($500.00). Withdrawals violating threshold are rejected with HTTP 422.
  • Current Account: Authorized overdraft limit ($1,000.00). Permits negative balances up to authorized threshold.
  • Account State: Blocked accounts reject all transactions with HTTP 403 Forbidden.

Atomic Fund Transfers

  • Validation: Verifies source/destination accounts and checks self-transfers (returns HTTP 400).
  • Synchronous Execution: Debits source (TRANSFER_OUT) and credits destination (TRANSFER_IN) atomically.
  • Audit Logging: Appends dual entries with unique transaction IDs to immutable ledgers.

LIFO Reversal Stack

  • Non-Destructive Undo: Banking compliance forbids deleting history; reversals execute compensating financial entries.
  • LIFO Sequence: Stack pops the most recent operation first, ensuring intermediate dependencies remain valid.
  • Balance Restoration: Perfectly restores pre-transaction account balances.

Smart Analytics & Anti-Money Laundering (AML)
Financial health grading and forensic graph cycle detection

Financial Health Auditor (SmartAuditor)

  • Inflow & Outflow Tracking: Aggregates deposits, salary credits, withdrawals, and merchant payments.
  • Savings Rate Formulation:
    Savings Rate = (Net Savings / Total Inflow) * 100%
  • Health Grading: Grades account health: EXCELLENT, HEALTHY, MODERATE, NEEDS_ATTENTION, CRITICAL.
  • Automated Advisory: Delivers actionable financial guidance (e.g. building 6-month emergency liquidity reserves).

AML Transaction Graph & Cycle Detection

  • Graph Modeling: Accounts form Vertices (V); inter-account fund transfers form Directed Edges (E = u → v) with monetary weights.
  • Wash Trading & Layering: Criminals route dirty money through multiple intermediary accounts to obscure origin.
  • 3-Color DFS Cycle Algorithm:
    Account A → Account B → Account C → Account A
    Uses recursion-stack state tracking (visited and inStack) in O(V + E) time.
  • Live React Visualizer: Renders the directed network dynamically and flags laundering rings with red alert badges.
Slide 11
Authentication & Security Architecture
Cryptographic PIN hashing vs Admin API authorization separation (docs/diagrams/02_auth_security_flow.svg)

Customer PBKDF2 PIN Security

  • Key Stretching: 10,000 rounds of HMAC-SHA256 (NIST SP 800-132).
  • Unique Salt: 128-bit CSPRNG salt generated via Windows CryptoAPI CryptGenRandom.
  • Constant-Time Equals: Bitwise XOR byte comparison neutralizes side-channel timing attacks.
  • Zero Plaintext Exposure: Stored as $pbkdf2-sha256$10000$<salt>$<hash>. Never exposed in API payloads or SQL dumps.

Admin API Authorization

  • Centralized Middleware: Intercepts all /api/admin/* routes.
  • Header Inspection: Validates incoming X-Admin-Key header.
  • Strict Rejection: Invalid keys immediately return HTTP 401 Unauthorized.
  • Customer Decoupling: Customer endpoints never require or expose admin credentials.

Slide 14
Limitations & Future Scope
Distinguishing the educational prototype scope from production enterprise infrastructure

Current Educational Limitations

  • Transport Security: The embedded Winsock2 server operates over HTTP. Production banking mandates TLS 1.3 / HTTPS to encrypt network traffic.
  • Memory-Hard KDF: PBKDF2 was chosen for portability; enterprise deployments prefer Argon2id (PHC winner) to resist ASIC/FPGA hardware attacks.
  • Administrative Auth: Uses shared X-Admin-Key header; production requires asymmetric RS256 JWTs or OAuth2 bearer tokens with refresh rotation.
  • Rate Limiting: No exponential backoff or 3-strike account lockout against brute-force attacks.
  • Persistence: Flat-file staging is designed for standalone offline operation, not multi-node clustered persistence.

Future Engineering Enhancements

  • HTTPS / TLS 1.3 Sockets: Integrate OpenSSL / Windows SChannel to encrypt data in transit.
  • Argon2id Password Hashing: Upgrade key derivation with memory-hard parameters ($m=64\text{MB}$, $t=3$, $p=4$).
  • Account Lockout Policy: Enforce 3-strike lockout and CAPTCHA challenges on consecutive failed PIN attempts.
  • Machine Learning AML Scoring: Real-time Graph Neural Network (GNN) transaction scoring for fraud classification.
  • Cloud Microservices: Decompose services with Docker containers and deploy on Kubernetes.
